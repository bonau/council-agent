# v0.9.7 User-owned Trust Grant Store Evidence

- Change: `trust-grant-store`
- Branch: `cursor/v097-trust-grant-store-d691`
- Baseline: v0.9.6 behavior, package metadata intentionally unchanged on the feature branch
- Scope: V1-008 persistent local store only; no Trust Tier runtime or decision matrix

## Security claim and threat boundary

v0.9.7 adds one strict, persistent authorization data source under the host user's data boundary. The default root is:

```text
${XDG_DATA_HOME:-~/.local/share}/council-agent/trust/
├── grants.json
├── grants.lock
└── audit/
    ├── events.jsonl
    └── events.jsonl.lock
```

The implementation accepts this state only on a POSIX local-user boundary with current-UID ownership, non-symlink components, user-only store directory/file modes, a non-group/world-writable user-owned creation ancestor, and no overlap in either direction with the active Agent workspace. Unsupported ownership or lock semantics, unsafe mode/type/owner, path overlap, and inspection/open failures are fail-closed.

This closes the supported product path in which project content or Agent workspace writes could create or restore a grant. It does not claim isolation from the same host user, root, hostile in-process Python, project code launched outside Council's product tools, or whole-control-plane rollback by a host attacker.

## Schema and canonical authority

`grants.json` has exactly one supported integer `schema_version: 1`, a monotonic document revision, and strict records with unknown fields forbidden. Each record contains:

- canonical UUID grant ID;
- subject masked principal reference and kind;
- recognized exact top-level action;
- finite canonical JSON resource object with no wildcard authority;
- sorted, unique, closed Council scopes;
- masked creator reference and kind;
- aware UTC creation and optional expiry;
- retained aware UTC revocation time and masked revoker reference.

Creation is self-grant only in this foundation. Requested grant scopes must already be present on the authenticated principal, and grant/revoke additionally require `high-risk:manage`. This makes the store incapable of expanding the caller's current principal declaration. Equivalent JSON key order/whitespace canonicalizes to the same target. Overlapping target intervals, duplicate IDs, conflicting records, malformed JSON/UTF-8, unknown fields/scopes/actions, non-integer/old/future schema, inconsistent revocation, and clock rollback reject the whole document.

Expired records are inactive at expiry. Revoked records remain as tombstones and are inactive on the next locked lookup and after reopening in another process.

## Authentication boundary

The public store API authenticates inside each grant, revoke, and list operation. It does not rely only on CLI wiring.

Each fresh one-use proof binds:

- masked acting principal;
- masked canonical user store root;
- non-empty per-invocation management session;
- purpose `trust-store-management`;
- exact operation and canonical arguments.

Grant/revoke require `high-risk:manage`; list requires `read`. Missing, replayed, expired, revoked, provider-error, wrong operation/arguments/store/principal/session proofs fail before grant state mutation. `OPENROUTER_API_KEY`, project policy, workspace content, session UUID alone, confirmation, `ConfirmMode.AUTO`, and `--yes` are not proof.

The CLI reads trust identity and `COUNCIL_AUTH_SECRET` directly from the host process environment and deliberately does not load project `.env` or require an OpenRouter credential:

```bash
council trust grant read_file '{"path":"README.md"}' --scope read
council trust list
council trust revoke <grant-id>
council trust list --all
```

No command-line secret, `--yes`, or `--trust-tier` option exists. The CLI explicitly labels this as a store foundation, not Trust Tier.

## Atomicity and concurrency

Every mutation:

1. validates and opens the fixed root without symlink following;
2. opens and descriptor-validates a fixed `0600` lock;
3. takes an exclusive inter-process lock;
4. re-reads and strictly validates current state;
5. applies one mutation and increments revision;
6. writes complete canonical JSON to a random same-directory `0600` file opened with create-exclusive/no-follow flags;
7. flushes the file;
8. atomically replaces `grants.json` using directory-relative descriptors;
9. flushes the directory and re-reads the committed document.

Tests inject partial-write and replace failures and assert the previous complete bytes remain valid with no temporary file adopted. A two-process spawn test concurrently commits distinct grants and observes revision 2 with both records and no lost update.

## Denial, bypass, and no-side-effect evidence

| Vector | Expected result | Side-effect assertion |
|---|---|---|
| Store inside/above workspace | `trust_store_workspace_overlap` | root/state not created |
| Unsafe root mode or simulated wrong UID | permission/ownership refusal | state unchanged/not created |
| Root symlink | `trust_store_unsafe_path` | target state not adopted |
| Malformed/unknown/future schema | corrupt/schema refusal | no partial grant returned |
| Duplicate ID/overlapping binding | whole-document refusal | no record adopted |
| Missing management proof | `trust_authentication_missing` | no `grants.json` |
| Wrong operation binding | `trust_authentication_denied` | no `grants.json` |
| Replay/expiry/revoked proof | `trust_authentication_denied` | requested grant absent |
| Principal lacks management scope | `trust_scope_insufficient` | provider cannot compensate; state absent |
| Requested scope exceeds current principal | invalid request | state absent |
| Project policy contains grant-like field | still requires host authentication | no store created without proof |
| Agent public `write_file` targets user store | `workspace_boundary` | store state absent/unchanged |
| Revoker is another principal | `trust_principal_mismatch` | original grant remains active |
| Atomic write/replace failure | `trust_store_io_failure` | prior bytes remain exact |
| Audit integrity failure | `trust_audit_failure` | next grant mutation does not occur |
| Stored grant with later narrowed principal | existing dispatcher `scope_insufficient` | tool target not written |

The final row is the v0.9.7 stopping-line test: persistent grants are not read by `SecurityContext` or middleware and therefore cannot alter product tool decisions.

## Masked audit evidence

Authentication lifecycle plus grant, revoke, list, and explicit lookup decisions are written to the user-owned trust audit. Records use the existing schema-v1 canonical event identity and sequence validation. Trust metadata contains operation/reason, correlation IDs, scope names, and only masked store, principal, creator, grant, action, and resource references.

Automated tests inspect raw `events.jsonl` and prove absence of:

- authentication verifier;
- raw principal ID;
- raw resource/path;
- raw grant UUID;
- challenge, response, and token values.

The operator CLI displays the raw grant ID because revoke requires it; the persisted audit does not.

## Backup, validation, restore, and downgrade

Recovery is intentionally offline and fail-closed:

1. Stop all Council processes using the store.
2. Preserve both current `grants.json` and `audit/` before any replacement.
3. Copy candidate state only through a host-user path outside every Agent workspace; keep directories `0700` and files `0600`.
4. Run validation-only inspection against the candidate. Validation opens without following symlinks and never creates, locks, repairs, truncates, migrates, or rewrites the candidate.
5. Compare document revisions and preserve every newer revocation. Never overwrite a higher known revision with an older backup.
6. Replace only with exact supported schema v1 after validation, using an offline atomic host-user operation.
7. Re-run validation and authenticated `council trust list --all`.

Schema 0, unversioned, future, or partially migrated state is rejected. There is no automatic downgrade or merge. A same-user/root attacker can roll back the complete store and audit together; cryptographic anti-rollback/remote anchoring is not part of v0.9.7.

## Accepted limitations and deferred work

- v0.9.7 does not map a grant to allow/confirm/deny and does not add grant state to `SecurityContext`.
- Trust Tier 0/1/2, `--trust-tier`, and the precedence decision matrix remain v0.9.8/v1.0-alpha work.
- No remote synchronization, team sharing, remote IAM, SSO/OAuth/WebAuthn, external signature, immutable sink, or anti-rollback anchor exists.
- POSIX file modes and advisory locks are defense within the local-user model, not an OS sandbox against the same user/root.
- Revoked/expired records are retained; authenticated compaction is future work.
