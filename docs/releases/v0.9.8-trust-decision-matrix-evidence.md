## Security claim

v0.9.8 defines one pure, deterministic decision vector and one normalized result used by the mandatory product dispatcher. The vector has exactly six non-secret dimensions:

1. restrict-only project policy;
2. current principal/scope authority;
3. exact-action authentication;
4. trust-grant applicability;
5. canonical action risk;
6. interaction disposition.

The only outcomes are `deny`, `require_confirmation`, and `allow`. `ConfirmMode` and `--yes` affect only dimension 6. They cannot create or replace any of dimensions 1–4.

This is a matrix contract and normalized evidence layer, not Trust Tier runtime. v0.9.8 does not define a tier enum, consume the user-owned grant store in product tools, accept `--trust-tier`, or map `AUTO` to Tier 2.

## Approved precedence

Matrix version 1 evaluates the complete vector in this fixed order:

| Priority | Dimension | Passing states | Denying / pending states | Stable winning reason |
|---:|---|---|---|---|
| 1 | Policy | `policy_allowed` | denied command / failed allowlist | `policy_denied`, `policy_not_allowed` |
| 2 | Principal/scope | `scope_allowed` | missing, revoked, invalid, mismatched principal; missing scope | `principal_missing`, `principal_revoked`, `principal_invalid`, `principal_mismatch`, `scope_insufficient` |
| 3 | Authentication | `authentication_not_required`, `step_up_allowed` | missing, invalid, failed, expired, revoked, replayed, binding mismatch, provider error | corresponding stable `authentication_*` reason |
| 4 | Grant | `trust_grant_not_required`, `trust_grant_allowed` | missing, invalid, revoked, expired, principal/grant scope insufficient | corresponding stable `trust_*` reason |
| 5 | Action risk | `read`, `mutate`, `high_risk` | unrecognized risk | `action_risk_unrecognized` |
| 6 | Interaction | read: `not_required`; mutate/high-risk: `auto`, `approved`, `compat_allow` | `pending`, `denied`, `refused` | `confirmation_required`, `confirmation_denied`, `confirmation_refused` |
| 7 | Completion | all preceding gates pass | — | `decision_allowed` |

Simultaneous denials always report the first matching row. Tests combine later `auto` approval with every earlier denial state. Policy deny wins over simultaneous scope denial; scope wins over authentication and grant; authentication wins over grant; grant wins over risk and interaction.

## `ConfirmMode` and `--yes` compatibility

The existing interaction behavior remains:

| Mode | Interaction-only behavior after authority passes |
|---|---|
| `ask` | returns pending until one prompt response; approval/denial applies only to that action |
| `auto` | automatically approves the interaction without a prompt |
| `refuse` | refuses an action that needs interaction |
| `compat` | compatibility-allows mutate actions and refuses high-risk actions |

Read actions use `not_required`. An approval is not persisted and does not issue an authentication token or grant.

CLI help now says that `--yes` skips interaction prompts only and does not grant scopes, authenticate, create a trust grant, or elevate privilege. `--yes` still resolves to `ConfirmMode.AUTO` for compatibility. A non-TTY invocation without `--yes` still resolves to `REFUSE`. These modes are never written into principal, authentication, or grant state.

## Runtime integration and entry-point consistency

`security.middleware.invoke()` is still the only product dispatcher. It maps existing scope/authentication decisions, project command policy, canonical risk, and handler-resolved interaction to the closed matrix. Runtime grant state is explicitly `trust_grant_not_required`; the dispatcher never constructs or calls `TrustGrantStore`.

The dispatcher adds one `metadata.trust_decision` object:

```json
{
  "matrix_version": 1,
  "outcome": "deny",
  "reason": "scope_insufficient",
  "vector": {
    "policy": "policy_allowed",
    "scope": "scope_insufficient",
    "authentication": "authentication_not_required",
    "grant": "trust_grant_not_required",
    "risk": "mutate",
    "interaction": "auto"
  }
}
```

Existing detailed `scope_authorization`, `session_authentication`, project-policy, classification, confirmation, and correlation metadata remain. Tracker, session, and result-audit records consume the same dispatcher-owned object. Crew adapters only format `ToolResult`; CLI only resolves and passes the context. Direct and Crew denials under equivalent contexts have byte-equivalent normalized matrix objects in result audit evidence.

An ordinary operational failure such as a missing readable file remains `ToolResult.success=False` but matrix `outcome=allow`, because authority passed and the operation itself failed. Tool limits, audit failures, and execution errors retain their existing outer refusal/error reasons; they do not become authority.

## Denial, bypass, and no-side-effect vectors

| Vector | Matrix result | Side-effect evidence |
|---|---|---|
| `AUTO` + missing mutate scope | `deny / scope_insufficient` | handler not called; file absent |
| command policy deny + missing shell/mutate scope + `AUTO` | `deny / policy_denied` | no subprocess; marker absent |
| high-risk scope + required authentication missing + `AUTO` | `deny / authentication_missing` | no subprocess; marker retained |
| required invalid grant + `AUTO` | `deny / trust_grant_invalid` | pure contract cannot mutate store or action |
| authorized mutate + `REFUSE` | `deny / confirmation_refused` | file absent |
| all authority passed + pending interaction | `require_confirmation / confirmation_required` | evaluator performs no prompt or operation |
| all authority passed + explicit approval | `allow / decision_allowed` | approval is one-action interaction only |
| matching persistent store record during product read | runtime vector grant is `trust_grant_not_required` | patched store lookup call count is zero |
| direct and Crew write with read-only principal | identical `scope_insufficient` vector/reason | both targets absent; two correlated result audits |
| `council run --trust-tier 2` | CLI parse refusal | no tier state/context exists |

## Masking and serialization

The pure matrix module has no context, filesystem, prompt, grant-store, CrewAI, or persistence dependency. Serialized evidence contains only matrix version, closed enum values, outcome, and reason. It has no fields for raw principal ID, resource, provider credential, verifier, challenge, response, token, or grant ID. Existing recursive audit/session sanitization remains in force around the normalized object.

## Deferred v1.0-alpha wiring

The reviewed contract lets v1.0-alpha add tier behavior without changing deny precedence. That future change must:

1. define Tier 0/1/2 as a separate typed input source;
2. translate a tier into grant requirements and prospective interaction only;
3. perform explicit exact grant lookup and pass its closed result into the vector;
4. never let a tier overwrite policy, scope, authentication, or invalid-grant states;
5. add `--trust-tier` only with authentication, docs, audit, migration, and end-to-end evidence;
6. version the matrix if any state or precedence changes.

## Accepted limitations

- Product grant consumption remains disabled. A matching v0.9.7 record does not alter a v0.9.8 tool action.
- The current confirmation prompt remains synchronous inside private security-aware handlers; normalized final evidence is dispatcher-owned.
- Policy/path checks and command containment are product boundaries, not an OS/process/network sandbox.
- The audit substrate remains per-event canonical identity/sequence, not an externally anchored hash chain.
- Hostile in-process Python and the same host user/root remain outside the supported isolation claim.
