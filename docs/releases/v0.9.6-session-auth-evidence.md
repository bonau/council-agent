## 結論

v0.9.6 新增與 session UUID、provider credential、principal scope、project policy、confirmation 和 grant 分離的 process-local authentication foundation。產品 orchestrator 會為每次 run 建立 non-empty runtime session ID 並啟用 high-risk step-up；當既有 cumulative scope decision 需要 `high-risk:manage` 時，dispatcher 在 confirmation／handler／subprocess 前要求 fresh、exact-action、one-use proof。

`--yes` 只把 confirmation mode 設為 `auto`。沒有 `COUNCIL_AUTH_SECRET` 時，即使 principal 有完整 scopes 且使用 `--yes`，high-risk action 仍以 `authentication_missing` fail closed；一般非 high-risk action 不需 authentication。Direct library `SecurityContext` 為相容性預設不啟用新 gate，可用 `require_high_risk_step_up=True` 明確採用相同行為，且不會把未啟用的 context 宣稱為 authenticated。

這不是 Trust Tier runtime、persistent grant/revoke store、遠端 SSO 或 host/OS isolation。Verifier、challenge 與 token state 只存在 process memory；restart 會使 outstanding challenge/token 失效，但 configured verifier 可重新認證。

## Threat model 與資料邊界

保護目標：

- session UUID 或 request ID 不能被當成 authentication；
- provider key、principal scope 或 confirmation approval 不能合成 step-up；
- proof 不能跨 principal、workspace、runtime session、purpose 或 exact action 使用；
- challenge/token 使用一次後不能重放；
- raw verifier、challenge、response、token 不進 audit、session、console 或本 evidence。

接受限制：

- hostile in-process Python caller 可 introspect memory，不在本版隔離保證；
- host owner/root、project test process 與 external process 不受 authentication manager 隔離；
- process-local revoke 不跨 restart 持久化；workspace 外 user-owned persistent store 屬 v0.9.7；
- 本版不定義 Tier 0/1/2 或完整 authorization precedence matrix。

## Challenge／token protocol

1. `AuthenticationBinding.for_action()` 建立 immutable binding：
   - masked principal reference；
   - canonical workspace path 的 `sha256:` reference；
   - non-empty runtime session ID；
   - `high-risk-action` purpose；
   - canonical top-level tool/args 的 `sha256:` reference。
2. `AuthenticationManager` 產生 unpredictable challenge ID + nonce，設定 issue/expiry，並只以 masked reference 索引 process-local state。
3. `answer_challenge()` 使用 typed `SecretStr` verifier 對完整 challenge envelope 做 HMAC response。
4. `complete_challenge()` 在 credential comparison 前先 consume challenge；成功才建立 random opaque `StepUpToken`。
5. `consume_step_up()` 在 expiry/freshness/binding comparison 前先 consume token；mismatch 後也不能再用正確 binding 重試。
6. Replay tombstone 保留於 manager lifetime；manager `revoke()` 後 outstanding state及新 challenge 全部拒絕。
7. 新 manager 不載入舊 state，因此 prior-process challenge/token 是 `authentication_invalid`。

Raw challenge ID、nonce、HMAC response 與 token 只包在 `SecretStr`／redacted `repr` 中；evidence 使用 digest reference。

## Product decision order

產品 high-risk action 的順序：

1. active `SecurityContext` validation；
2. current principal identity + cumulative scope decision；
3. `require_high_risk_step_up` + `high-risk:manage` 判定；
4. exact-action challenge/response + fresh token consume；
5. middleware attempt evidence；
6. tool-specific containment、project policy、confirmation；
7. operation、tracker、result/session/audit evidence。

Scope 不足時不嘗試 authentication。Authentication allow 只代表可進入後續 gates；policy deny 或 confirmation refuse 仍拒絕。`test_authentication_does_not_override_confirmation_or_policy` 覆蓋這兩條路且 subprocess call count 為 0。

Stable authentication reasons：

- `authentication_not_required`
- `authentication_missing`
- `authentication_invalid`
- `authentication_failed`
- `authentication_expired`
- `authentication_revoked`
- `authentication_replay`
- `authentication_binding_mismatch`
- `authentication_provider_error`
- `step_up_allowed`

## Audit／session／console 遮罩

`AuthenticationManager` 透過 generic event sink 產生 credential-free lifecycle event；orchestrator 將其接到 schema-v1 administrative `session_auth` result。事件只含 event type、stable reason、binding digest、challenge/token digest reference、request/session correlation。Tool attempt/result與 session tool line的 `metadata.session_authentication` 使用同一 normalized decision。

Lifecycle event types：

- `authentication_success`
- `authentication_failure`
- `authentication_expiry`
- `authentication_revocation`
- `authentication_replay`

`test_durable_lifecycle_matrix_masks_all_raw_authentication_values` 在同一 verified audit JSONL 實際產生五種 event，並逐一斷言 raw verifier、challenge ID、nonce、HMAC response 與 token 不在檔案。`test_sandboxed_service_step_up_succeeds_with_masked_evidence` 證明 sandbox run 的 auth success ×2、tool attempt/result、cleanup revoke 共用同一 session，session `tools.jsonl` 只保留 masked `step_up_allowed` decision。`test_cli_passes_dedicated_secret_without_displaying_it` 證明 CLI 只顯示 `configured`，不顯示 auth/provider secret，且沒有 `--auth-secret` process-argument option。

## 相容性與操作

- CLI/service automation：設定 `COUNCIL_AUTH_SECRET` 才能為 product high-risk action 建立 fresh proof；此值以 `SecretStr` 載入，不提供 command-line secret option。
- `--yes`：只處理 confirmation，不能建立 manager、answer challenge、mint/consume proof 或覆蓋 authentication denial。
- Library：`SecurityContext.create(..., require_high_risk_step_up=True, authentication_manager=..., step_up_provider=...)` 可採用同一 gate；預設 disabled 保留既有 direct-library behavior。
- Restart／crash：舊 token 無 state 可匹配而拒絕；重新設定 verifier只能建立新 challenge/token，不能恢復舊 proof。
